# Codex Workbench v0.1 MVP Scope Freeze

Date: 2026-08-30
Status: FROZEN FOR v0.1
Baseline product head: `68faf1ce38c1bd39aadcad3ed3d6382fd3d8a599` (PR #48)

## 1. Decision

The v0.1 goal is intentionally reduced to a usable basic product. Workbench must stop expanding into every long-term Automation idea before the first usable release.

From this checkpoint onward, v0.1 development prioritizes integration, end-to-end validation, usability cleanup, Windows packaging, and bug fixing. New large product systems do not enter v0.1 unless they are required to complete the frozen end-to-end acceptance path below.

## 2. v0.1 product goal

A user can use normal Codex capabilities inside a Product Project, inspect basic project/conversation context, and complete one basic Automation workflow from a user goal through execution and completion.

Workbench continues to rely on Codex-native runtime behavior for Thread/Turn/Item, context and compaction, tools, sandbox/approvals, subagents, and runtime lifecycle. v0.1 must not rebuild these capabilities.

## 3. Required for v0.1

1. **Normal Codex workflow**
   - create/resume native Codex conversations;
   - use Codex tools and code-editing behavior without a second Workbench runtime.

2. **Product Project management**
   - create/open/remove/rename Product Projects;
   - associate native Threads with a project;
   - preserve project state across app restart.

3. **Basic Map experience**
   - Conversation Map remains usable;
   - Project Map remains usable;
   - no new heavy dashboard is required for v0.1.

4. **Basic Automation workflow**
   - create and associate an AutomationProject from the Product Project UI;
   - enter a goal;
   - Requirement alignment/draft;
   - USER confirmation;
   - Planner creates a Plan;
   - execute the current Step using an explicit Native Thread target;
   - reconcile when required;
   - verify result;
   - review/gate/advance using the already implemented governance path;
   - finish the Plan/Project.

5. **Windows runnable package**
   - produce a Windows package/executable;
   - verify first launch and basic runtime startup on Windows;
   - verify the frozen v0.1 end-to-end path on a real packaged build.

## 4. Explicitly deferred beyond v0.1

The following are not release blockers for v0.1:

- fully automatic continuous multi-step execution;
- attention/notification center ("only call me when needed");
- user-facing mid-project Requirement Change workflow;
- automatic impact analysis and automatic Replan UX;
- standalone Workflow Map/dashboard;
- parallel Step scheduling and advanced resource scheduling;
- generalized hardware/deployment/GUI adapters;
- expanded multi-provider/WebGPT product experience;
- cloud sync and team collaboration;
- enterprise permissions;
- advanced backup UI;
- automatic updater product flow;
- other large new Automation subsystems that are not required for the v0.1 acceptance path.

Existing backend code for future capabilities is not removed merely because the feature is deferred. The scope freeze controls what must be productized before v0.1.

## 5. v0.1 acceptance path

v0.1 is considered functionally complete when this path can be executed reliably on a packaged Windows build:

1. Launch Workbench.
2. Create a Product Project for a real local code repository.
3. Create/open a native Codex Thread and use normal Codex coding behavior.
4. Inspect the available Conversation/Project Map experience.
5. Create a new AutomationProject from the Product Project UI and associate it.
6. Enter a task goal.
7. Produce and inspect the Requirement draft.
8. Answer required questions and confirm the Requirement as USER.
9. Generate a Plan using the explicit current Native Thread target.
10. Execute the current Step.
11. Reconcile if needed.
12. Verify and review the Step result.
13. Pass the Stage gate and advance until the Plan is complete.
14. Complete the AutomationProject.
15. Close Workbench.
16. Reopen Workbench and confirm Product Project, native conversation binding, and Automation workflow state remain usable.

Manual user clicks between governance stages are acceptable in v0.1. Fully autonomous continuation is deferred.

## 6. Remaining release work after PR #48

The mainline focus is now limited to:

1. integrate the current stacked product changes into one coherent v0.1 candidate head;
2. simplify/clean the existing Automation UI only where required to make the acceptance path understandable;
3. run the complete real end-to-end acceptance path;
4. package and test the Windows build;
5. fix defects discovered by the integrated E2E/package run;
6. run final regression and produce the v0.1 build.

The repository-owned model benchmark remains incremental test debt. Previously passing formal model trials are not repeated solely to obtain a new run. Unresolved A/B cases remain tracked separately and do not block ordinary v0.1 implementation work unless a release decision explicitly requires them.

## 7. Delivery expectation

At the time of this freeze, the remaining v0.1 effort is estimated at roughly **3-5 normal development days (about 20-35 engineering hours)**, with a conservative range of 5-7 development days if packaged Windows E2E exposes significant integration defects.

This estimate assumes the v0.1 scope above remains frozen and no new large features are added before the first usable release.

## 8. Scope-control rule

Before adding any new feature to the v0.1 mainline, ask one question:

> Is this required to make the frozen v0.1 acceptance path complete, understandable, reliable, or packageable?

If the answer is no, defer it to a later version instead of expanding v0.1.
