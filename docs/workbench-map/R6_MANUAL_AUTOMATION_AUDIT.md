# R6 Manual / Automation Decouple Audit

## Result

`R6 — Manual / Automation Decouple` is an `AUDIT_PASS` at source checkpoint `68d813b707326e4079992c26435bfbe53a148982`.

No production code change was justified. Manual V1 startup and Native Thread/Turn execution remain independent of Automation initialization, and the Workbench product `ProjectRecord` remains a separate persisted identity from Automation `AutomationProject`.

## Manual startup independence

`src/main/startup-policy.ts` explicitly defines ordinary GUI startup as idle with respect to optional Automation/WebGPT state. `createStartupPlan()` sets `automationAtStartup` only for explicit Automation gates, and `runStartupPlan()` calls `initializeAutomation()` only when that flag is true.

`tests/arch-v2-8-startup-idle.test.ts` locks this down with filesystem/store evidence:

- ordinary GUI startup produces no Automation/control-plane events;
- no `AutomationStore` is constructed;
- the filesystem snapshot is unchanged;
- no automation/webgpt/sqlite/control artifacts appear;
- explicit WebGPT control requests and explicit persistence smoke remain opt-in activation paths.

The normal Main process creates the window and then executes this startup plan. `ensureAutomationPersistence()` is a lazy Automation/WebGPT boundary, not a prerequisite for the ordinary manual runtime.

Classification: `MANUAL_INDEPENDENCE_PASS`.

## Manual execution path

The renderer/preload exposes manual Native operations through `native-runtime:*` IPC channels. The Main handlers route directly to the selected `NativeThreadRuntime` / runtime registry:

- start -> `startCurrentRuntime()`;
- resume/switch -> Native runtime selection/resume;
- read -> `NativeThreadRuntime.readThread()`;
- turn -> exact selected Native target check, then `startTurnAccepted()` with native composer options;
- approval/interrupt/server requests remain Native runtime/server-request paths.

No Workflow, RequirementVersion, PlanVersion, AutomationProject, or AutomationStore prerequisite was found in the manual Thread/Turn path.

Automation depends in the other direction when it deliberately uses the Native provider adapter: it may submit only through an already-attached Native runtime and fails closed if that target is unavailable. This shared infrastructure does not make Manual depend on Automation.

Classification: `MANUAL_INDEPENDENCE_PASS`.

## Product Project ownership

Workbench product Project truth is `ProjectRecord` in the V1 persistence document:

- identity: `ProjectRecord.projectId`;
- product data: name, cwd, timestamps, metadata;
- relationships: ThreadProjection -> product project for navigation/cwd grouping.

`V1PersistenceStore.createProject()` generates its own UUID when no projectId is supplied. The renderer's normal create flow passes only `{ name, cwd }`, so ordinary product Project identity is generated by V1 persistence rather than copied from Automation.

`tests/persistence-store.test.ts` exercises this as an independent `workbench-state.json` store containing Projects and ThreadProjections.

## AutomationProject ownership

Automation Project truth is a different entity in Automation persistence:

- identity: `AutomationProject.projectId`;
- workflow data: lifecycle, active RequirementVersion, active PlanVersion, PolicyVersion, revision;
- owner: AutomationStore / `automation.db`.

`AutomationStore.createAutomationProject()` generates an Automation ID when no explicit ID is supplied. Requirement alignment starts with `tx.require("automationProjects", projectId)`. Planner creation similarly searches `snapshot.automationProjects` and throws `PROJECT_NOT_FOUND` if the AutomationProject does not exist.

`tests/automation-foundation.test.ts` explicitly verifies an independent SQLite `automation.db` and verifies migration does not import V1/WebGPT state.

The production control-plane commands also describe their input as an Automation project and pass that ID only into Automation services. No production path was found that automatically creates an AutomationProject from the currently selected product Project or assumes the IDs are equal.

Classification: `IDENTITY_BOUNDARY_PASS`.

## Legacy ExternalRef naming

Automation v4 retains `WORKBENCH_PROJECT` as the serialized carrier kind for a provider workflow `SCOPE`. This name is compatibility vocabulary, not Product Project ownership.

`src/automation/workflow-provider-reference.ts` explicitly states that carrier kind names are legacy serialization vocabulary: `ExternalRef.provider` is authoritative for provider identity, while the neutral envelope is authoritative for workflow role. Provider-aware Requirement code writes the neutral scope envelope into this legacy carrier.

This ExternalRef correlation does not read, create, update, or own `ProjectRecord` in V1 persistence and therefore is not an identity collapse.

## Separation matrix

| Concern | Product Project | AutomationProject |
| --- | --- | --- |
| Persistence | V1 Workbench persistence (`workbench-state.json`) | Automation persistence (`automation.db`) |
| Primary role | Product shell, cwd, navigation, Thread grouping | Workflow/governance project lifecycle |
| Normal creation | Renderer -> V1 persistence, UUID generated there | Explicit AutomationStore creation |
| Native Thread relation | ThreadProjection may bind to product Project | Native IDs only through explicit provider/evidence/external refs |
| Requirement/Plan lifecycle | None | Owns active RequirementVersion/PlanVersion/PolicyVersion refs |
| Startup requirement | Available on ordinary GUI path | Lazy/explicit Automation activation only |

## Exit decision

R6 exit condition is satisfied:

> Manual V1 remains independent of Automation and Workbench Project remains distinct from AutomationProject.

No `DECOUPLE_CHANGE` was proven, so no R6 production branch or adapter layer should be created merely for architectural symmetry.

The next active stage is `R7 — Projection / Map`.
